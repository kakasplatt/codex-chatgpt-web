# Graphify Repository Analysis Guide

This document defines how agents should use Graphify in `codex-chatgpt-web` for architecture discovery, debugging, code review, planning, implementation support, and verification.

The repository already maintains a Graphify knowledge graph under `graphify-out/`. The normal workflow is therefore to query the existing graph, use it to locate relevant code and relationships, and then confirm material conclusions against the current repository state.

## 1. Scope and authority

This guide applies whenever an agent:

- invokes Graphify directly;
- answers a repository question using `graphify-out/graph.json`;
- uses Graphify to trace dependencies, calls, imports, ownership, or architectural boundaries;
- uses Graphify findings to plan or review a change;
- combines Graphify with Superpowers or parallel-agent workflows;
- considers rebuilding or incrementally updating the graph.

Instruction priority is:

1. system and runtime instructions;
2. explicit user instructions for the current task;
3. repository `AGENTS.md` instructions;
4. this guide;
5. Graphify's installed skill defaults.

If the user explicitly requests a Graphify command or mode, honor that request unless a higher-priority instruction prevents it. If the user asks only a natural-language question about the repository, follow the query-first workflow in this document.

## 2. What Graphify is for in this repository

Graphify is an architecture and relationship index. It turns repository content into a persistent graph whose nodes and edges can expose connections that are expensive to discover through repeated text search alone.

Use it to answer questions such as:

- What calls or depends on this symbol?
- Which files participate in a browser-turn lifecycle?
- How does one subsystem reach another?
- Which components sit between an entry point and a failure site?
- Which architectural community contains a symbol?
- What is the shortest relationship path between two concepts?
- Which nearby symbols should be inspected during a review?

Graphify should accelerate discovery. It does not replace direct inspection of the code that currently exists in the worktree.

## 3. Repository Graphify artifacts

The primary artifacts are:

| Artifact | Purpose |
| --- | --- |
| `graphify-out/graph.json` | Persistent machine-readable knowledge graph used by `query`, `path`, and `explain`. |
| `graphify-out/GRAPH_REPORT.md` | Human-readable graph report, communities, notable nodes, and suggested questions. |
| `graphify-out/graph.html` | Interactive visualization generated by Graphify. |
| `graphify-out/manifest.json` | Incremental extraction state used to determine new, changed, and deleted files. |
| `graphify-out/reflections/LESSONS.md` | Accumulated useful paths, dead ends, and corrections when Graphify memory/reflection has been used. |
| `graphify-out/memory/` | Saved query outcomes used by Graphify's feedback loop. |

`graphify-out/` is ignored by Git in this repository. Changes inside it are local analysis artifacts and must not be confused with source-code changes.

The presence of `graphify-out/graph.json` is the main fast-path signal. When it exists, ordinary repository questions should start from the graph instead of rebuilding it.

## 4. Mandatory decision flow

Use this decision order before running Graphify:

1. Check whether `graphify-out/graph.json` exists.
2. Classify the user's intent.
3. For a natural-language repository question, query the existing graph.
4. For a relationship between two named concepts, use `graphify path`.
5. For one symbol or concept and its neighborhood, use `graphify explain`.
6. Run an incremental update only when freshness of the graph itself is explicitly required.
7. Run clustering only when the user specifically wants communities/report regeneration.
8. Run a full extraction only when the graph is absent, the user explicitly requests a rebuild, or a full rebuild is otherwise required by the task.

Do not run detection, extraction, clustering, or a full rebuild merely because a question is difficult. An existing graph is intended to be queried first.

## 5. Session bootstrap for graph work

For repository-analysis work that will use Graphify, begin with a lightweight check:

```powershell
Test-Path graphify-out/graph.json
graphify --version
```

If Graphify memory has been used and the installed CLI supports reflection, refresh deterministic lessons and inspect them before choosing a path through the graph:

```powershell
graphify reflect --if-stale
Get-Content graphify-out/reflections/LESSONS.md
```

Treat reflection as supporting context. A prior saved outcome can point to a preferred source, a known dead end, or a correction, but it does not override current source code.

If `graphify-out/graph.json` is missing, do not pretend a graph query succeeded. Build or update only according to the task's requested scope.

## 6. Query-first workflow

When the graph exists and the user asks how the repository works, run a query against the existing graph before broad source scanning.

```powershell
graphify query "<question>"
```

Examples:

```powershell
graphify query "How does an accepted ChatGPT submission reach response tracking?"
graphify query "What uses ChatGptTurnDomHealthTracker?"
graphify query "Which components participate in retained compaction recovery?"
```

The default query traversal is breadth-first search. It is suitable for broad context and nearest relationships.

Use depth-first traversal when the question is explicitly about a chain or dependency path:

```powershell
graphify query "browser send activation response recovery" --dfs
```

Use a larger token budget only when the returned subgraph is too small to support the task:

```powershell
graphify query "browser send activation response recovery" --dfs --budget 3000
```

Avoid increasing the budget by default. Start with the smallest graph slice that can identify the relevant files and symbols.

## 7. Query vocabulary and multilingual questions

Graphify's node matcher is based on graph labels and does not provide general synonym, stemming, or cross-language reasoning by itself. A Portuguese question can therefore miss English identifiers unless the query is expanded using vocabulary that actually exists in the graph.

When a direct natural-language query produces weak or empty matches:

1. inspect labels or vocabulary from the existing graph;
2. choose only terms that are present in that graph;
3. map the user's concept to those existing labels;
4. rerun the query using the constrained terms;
5. keep the original user intent when explaining the result.

Do not invent search terms and present them as graph evidence. If the graph contains no vocabulary corresponding to the concept, say that the graph did not provide a useful match and continue with direct repository inspection.

## 8. Choosing query, path, and explain

Use the smallest Graphify operation that matches the question.

| Need | Command | Typical use |
| --- | --- | --- |
| Broad neighborhood or architecture context | `graphify query "..."` | Find relevant files, nearby symbols, and architectural communities. |
| Trace a specific chain | `graphify query "..." --dfs` | Follow a dependency or lifecycle path. |
| Shortest connection between two concepts | `graphify path "A" "B"` | Determine how two subsystems are linked. |
| Understand one node and its neighbors | `graphify explain "X"` | Inspect one symbol's role and surrounding relationships. |

Examples:

```powershell
graphify path "callTurnBroker" "ChatGptTurnDomHealthTracker"
graphify explain "classifySendFailure"
```

If a named concept is ambiguous, use repository-qualified or symbol-specific terms and confirm the returned node's `source_file` or `source_location` before relying on it.

## 9. Graph evidence and source confirmation

Graphify output is discovery evidence. Material behavioral conclusions require confirmation from the current repository.

After a graph query identifies relevant nodes:

1. note the node labels, edge relationships, confidence, and source locations;
2. open the cited source files and inspect the relevant implementation;
3. inspect the current diff when the worktree is dirty or the task concerns an in-progress change;
4. use Git history or blame when the question is historical or causal;
5. run focused tests when the claim depends on runtime behavior;
6. broaden verification only when the focused evidence leaves a meaningful gap.

For code review, a Graphify edge can justify inspecting a call site or dependency. It is not sufficient by itself to report a regression.

For debugging, a graph path can identify likely boundaries. Reproduction, logs, source behavior, or tests must establish the actual failure mechanism.

For architecture explanations, cite Graphify's `source_location` when available, then confirm the described relationship in source if it materially affects a decision.

## 10. Confidence and honesty rules

Graphify can distinguish extracted, inferred, and ambiguous relationships. Preserve that distinction.

- `EXTRACTED` relationships originate from direct structural or content evidence.
- `INFERRED` relationships are semantic connections inferred during extraction and require more caution.
- `AMBIGUOUS` relationships explicitly represent uncertainty.

Never upgrade an inferred or ambiguous edge into a confirmed fact merely because it fits a plausible architecture story.

When evidence is incomplete:

- state what the graph shows;
- state what direct source inspection confirms;
- state what remains uncertain;
- avoid inventing missing edges or paths;
- do not treat a missing graph result as proof that no relationship exists.

Graphify's own honesty rules also require that agents never invent an edge and that graph-health or corpus warnings are surfaced instead of hidden.

## 11. Freshness and incremental update policy

Ordinary repository questions do not justify rebuilding the graph.

Use an incremental update when the task explicitly requires Graphify to incorporate new or changed files:

```powershell
graphify update .
```

Incremental update is preferable to a full rebuild because it re-extracts changed code and merges it with the existing graph.

Before updating:

- preserve unrelated source changes;
- inspect `git status --short --branch`;
- remember that `graphify-out/` is local analysis state;
- do not delete existing graph artifacts merely to force a clean rebuild.

After updating, verify that `graphify-out/graph.json`, `manifest.json`, and the report were refreshed and that Graphify did not report graph-health failures.

If the update reports deleted files, ensure the merge pruned those sources instead of leaving stale nodes.

## 12. Full rebuild policy

A full extraction is appropriate when:

- no usable graph exists;
- the user explicitly requests a rebuild or fresh extraction;
- an incremental update cannot safely represent the requested corpus change;
- the graph is demonstrably corrupt and rebuilding is part of the authorized task.

The installed CLI exposes full extraction through:

```powershell
graphify extract .
```

Use deep semantic mode only when richer inferred relationships are actually needed:

```powershell
graphify extract . --mode deep
```

Deep mode can create more inferred edges. Treat those edges as hypotheses until source evidence confirms them.

Do not use `--force` casually. Graphify protects an existing graph from accidental shrinkage. Override that protection only when the smaller graph is intentional and the task requires it.

## 13. Cluster-only policy

Use cluster-only when the graph content is already correct and only community detection or generated reports need to be refreshed:

```powershell
graphify cluster-only .
```

Cluster-only is not a substitute for updating changed source files. It reorganizes the existing graph; it does not make stale nodes current.

## 14. Graph health and integrity

Treat Graphify health warnings as analysis limitations.

Relevant failure modes include:

- missing edge endpoints;
- dangling endpoints;
- unintended self-loops;
- collapsed reciprocal edges in a directed graph;
- a graph unexpectedly shrinking during export;
- stale nodes surviving an incremental update;
- changed semantic files being incorrectly treated as already extracted.

If Graphify reports an integrity problem, do not hide it and continue as though the graph were complete. Use direct source inspection for the active task and repair or rebuild the graph only when that work is in scope.

## 15. Directed relationships

Call direction, imports, implementation, and other asymmetric relationships can matter during debugging and review.

If a task depends on directionality, verify whether the graph was built as directed before drawing conclusions from an edge path. A generic undirected connection proves association, not call direction.

When direction is materially important and the existing graph cannot establish it, inspect the source directly or rebuild/update with directed extraction when explicitly authorized by the task.

## 16. Integration with Superpowers

When the user invokes both Superpowers and Graphify, apply both repository policies.

Read [`../superpowers/model-selection.md`](../superpowers/model-selection.md) before invoking a Superpowers skill or dispatching Superpowers subagents.

Use Graphify during Superpowers workflows as follows:

| Phase | Graphify role |
| --- | --- |
| Brainstorming / design | Map affected communities, boundaries, dependencies, and candidate integration points. |
| Planning | Identify concrete files, symbols, call paths, and neighboring modules that the plan must account for. |
| Debugging | Trace the failure path and find code boundaries to inspect; logs and reproductions establish the root cause. |
| Atomic implementation | Re-query when needed to understand local dependencies before editing; source remains authoritative. |
| Code review | Find related call sites, affected consumers, and cross-module paths that deserve review. |
| Verification | Use Graphify to check analysis coverage; use tests, typechecks, builds, or live smoke tests for behavioral proof. |

Graphify does not change Superpowers approval or design gates. If a Superpowers workflow requires investigation and design before implementation, Graphify supports that investigation; it does not authorize edits by itself.

## 17. Parallel-agent use

When several agents investigate independent parts of a problem, Graphify can provide a shared architecture map.

Recommended pattern:

1. one coordinating agent identifies graph communities or paths;
2. workers receive bounded source areas or symbols from that map;
3. each worker confirms findings in source rather than repeating graph claims;
4. the coordinator reconciles cross-module findings;
5. final review checks behavior and integration across the combined change.

Do not have multiple workers rebuild the same graph concurrently. Querying the same existing graph is safe; extraction and update operations should be coordinated as a single repository-level action.

## 18. Code-review workflow

For review requests, use Graphify to increase coverage without inflating findings.

Recommended sequence:

1. inspect the requested diff and repository status;
2. query changed symbols or subsystems in Graphify;
3. identify callers, consumers, lifecycle neighbors, and cross-module paths;
4. inspect those source sites directly;
5. test concrete risk hypotheses;
6. report only demonstrated defects or clearly bounded residual validation gaps.

Do not report a finding solely because two changed files appear in the same graph community.

Do not infer historical authorship from Graphify. Use Git history and blame for authorship and commit-impact questions.

## 19. Debugging workflow

For a concrete failure, logs and observed lifecycle events should narrow the Graphify query.

Recommended sequence:

1. identify the failing event, symbol, trace, or state transition;
2. query or explain the relevant Graphify node;
3. use `path` or DFS when a cross-module chain is suspected;
4. inspect the exact implementation along that path;
5. reproduce the failure or encode the failing behavior in a focused test;
6. implement only after the root cause is supported by direct evidence;
7. verify the fix along the same behavioral path.

If Graphify and runtime evidence disagree, investigate the current source and graph freshness. Do not force runtime evidence to fit the graph.

## 20. Implementation workflow

Before editing code based on Graphify:

- inspect every source file that materially supports the proposed change;
- inspect relevant tests and public contracts;
- account for current uncommitted changes;
- preserve unrelated worktree state;
- keep the change bounded to the user's requested behavior.

After editing:

- run focused verification for the modified behavior;
- re-query Graphify only when it helps check related call sites or architectural coverage;
- update the graph only when current graph freshness is itself part of the requested deliverable.

## 21. Saving Graphify results

Graphify supports saving useful, dead-end, or corrected outcomes into its local feedback loop through `save-result` and `reflect`.

Use this feature only when persisting analysis context is useful for future Graphify work. Saved outcomes are analysis memory, not source-of-truth documentation.

Useful outcomes should reference the graph nodes that actually supported the answer. Dead ends should be recorded only when the explored path was genuinely unhelpful. Corrections should state the corrected result clearly.

Never use a saved Graphify answer as a substitute for rechecking source after the repository changes.

## 22. Windows and PowerShell notes

This repository is commonly operated from PowerShell on Windows.

Prefer native PowerShell commands for repository inspection around Graphify:

```powershell
git status --short --branch
Get-Item graphify-out/graph.json
Get-Content graphify-out/GRAPH_REPORT.md
Select-String -Path src\**\*.ts -Pattern "SymbolName"
```

Do not copy Bash-only helper snippets from Graphify's skill into PowerShell unchanged. Prefer the installed `graphify` executable for `query`, `path`, `explain`, `update`, `cluster-only`, `reflect`, and `extract`.

If an advanced fallback requires Python, resolve the interpreter deliberately instead of assuming `python3` exists on Windows.

## 23. Reporting requirements

When Graphify materially contributes to an answer or implementation decision, make the evidence auditable.

Report, as appropriate:

- the Graphify operation used;
- the relevant node or path;
- the source location supplied by the graph;
- whether the relationship was extracted, inferred, or ambiguous;
- the direct source evidence that confirmed the conclusion;
- tests or runtime evidence used for behavioral claims;
- any freshness or integrity limitation that remains relevant.

Keep Graphify mechanics concise in the final user-facing answer. The goal is to show enough evidence to assess the conclusion, not to narrate every traversal step.

## 24. Anti-patterns

Avoid these behaviors:

- rebuilding the graph before every repository question;
- running `graphify update .` automatically for a read-only question;
- treating a graph edge as runtime proof;
- inventing an edge when the graph lacks one;
- treating no query hit as proof that a symbol or relationship does not exist;
- ignoring `source_location` and relying only on node labels;
- using Graphify for Git authorship or commit ancestry when Git provides authoritative evidence;
- using cluster membership as proof of a direct dependency;
- ignoring inferred or ambiguous confidence;
- using `--force` to bypass a shrink guard without understanding why the graph became smaller;
- rebuilding from multiple parallel agents at the same time;
- modifying unrelated source files while performing Graphify-only analysis.

## 25. Compact operational policy

Agents can apply the following compact rule during normal work:

> If `graphify-out/graph.json` exists, query it first for repository questions. Use `path` for two-concept relationships and `explain` for one-node neighborhoods. Treat the graph as a navigation index, then confirm material claims in the current source, diff, Git history, logs, and tests. Do not rebuild or update the graph unless freshness or extraction is explicitly part of the task. Preserve confidence and uncertainty; never invent graph relationships.

## 26. Maintenance

Review this document when:

- Graphify changes its CLI contract;
- the repository changes where Graphify artifacts live;
- the Graphify skill changes its query, update, confidence, or reflection semantics;
- the Superpowers workflow changes in a way that affects Graphify coordination;
- repeated repository work reveals a missing safety, freshness, or evidence rule.

When updating this guide, verify the installed Graphify CLI and skill rather than relying on stale command examples.
